# Host-authoritative multiplayer (prototype)

## Authority model

The player who creates the room is the sole simulation authority. Their browser owns the `LocalGameServer`, advances the simulation, validates the incoming command envelope at the transport boundary, and publishes a versioned `GameWorldFrame` as a full state only on join or recovery, and uses revision-based state deltas for ordinary replication. The guest never advances a second authoritative simulation and never creates a placeholder local world: it renders only a snapshot projected from a validated host-authoritative frame and sends commands through the reliable direct WebRTC data connection created by PeerJS by default. The guest does not expose its session/snapshot until both the participant assignment and an authoritative frame have arrived.

PeerJS Cloud registers the host ID and signals the direct connection; it does not host the simulation or relay normal game data. The game-message adapter remains transport-neutral. The unused self-hosted WebSocket relay and developer mode have been removed from the production project.

## Room versus world lifecycle

Creating a room registers connections and a room roster; it does not start or publish a game world. The host explicitly starts a world from the room, which creates a fresh `worldId` and sends an assignment followed by the full baseline. Pause/resume stops and restarts the same world's simulation clock. Returning to the room ends the current world, clears replication baselines, and leaves connected participants, chat, and heartbeat traffic alive. The next explicit start replaces the stopped runtime with a new world. TEAM/FFA defeated participants may be revived in-place with a distinct Core; CO-OP uses a shared Core and therefore requires a fresh world for team revival.

Room status is a room-level control stream, ordered by `statusRevision` independently of world revisions. It is accepted only after `game-player-assigned` establishes `roomSessionId`; when `hasWorld` is true, its `worldId` must match the assignment. Heartbeat and chat traffic never use the world ID as their liveness/session boundary. See the [runtime responsibility map](multiplayer-runtime-map.md) for the full lifecycle sequence and the owner of each boundary.

## Network constraints

- The default uses PeerJS Cloud signalling plus direct WebRTC data channels. This release configures STUN but does not include TURN credentials, so some restrictive NAT/firewall networks cannot connect directly. No local WebSocket relay fallback is shipped.
- PeerJS Cloud is a shared free signalling service. A new join after disconnect is supported as a fresh participant, not as session resume: the previous participant and active assets are removed, and the new assignment starts alive with no inherited defeat timestamp. Authentication, room passwords, TURN, and full hardening against hostile clients remain future work.
- The room currently supports eight participants total (the host plus up to seven guests), with a host-side router assigning a unique participant identity per transport peer. Each client controls a separate commander and has a private resource ledger; the host applies the selected Free-for-all, Team, or Cooperative core/alliance rules. Per-peer command limits, resync throttling, heartbeat expiry, and bounded full-state retries are implemented; authentication and hardened authorization remain future work.
- Host tab closure stops the simulation. No authoritative state is persisted on the signaling server.
- The host publishes state deltas at 30 Hz. Room roster/phase changes are sent immediately, while the room clock is coalesced to at most 1 Hz. The host captures replication candidates at the same 30 Hz cadence. A complete state is sent on join/recovery only; regular updates contain only changed fields and stable-key collection mutations. Empty deltas are skipped. Pointer aim messages are throttled to 30 Hz to prevent mouse movement from flooding the data channel. Guests interpolate remote render poses and predict only their local Commander presentation; host simulation and combat remain authoritative.

## Protocol

- `game-hello`: guest declares command protocol v2 and state-sync protocol v3. The PeerJS application handshake is protocol v2; peers using earlier versions are rejected before the room connection is accepted. The host registers the participant and sends `game-player-assigned`, then `game-initial-state` with the authoritative `GameWorldFrame`; the frame includes the 32-bit `worldSeed` and initial state. The client does not generate a placeholder world.
- `game-player-assigned`: host binds the transport peer to its participant ID, declares the required state-sync protocol version, and includes the authoritative `worldId`. The world ID is part of the assignment contract, not an inference from whichever full frame arrives first. A participant ID may change on the same transport only when the assignment explicitly announces a different world.
- `game-initial-state`: full frame used for initial join, explicit resynchronization, an explicitly assigned authority-world handoff, and retransmission until its revision is acknowledged. The seed is carried once inside the frame, not duplicated in the envelope or repeated in regular deltas.
- Authority handoff: when a live direct connection survives replacement of the host runtime/world, the host sends a new assignment with the new `worldId` before its full-state baseline. The guest holds a full state for an unknown world until the matching assignment arrives, then resets world-scoped sequencing/prediction/deduplication and accepts the baseline. It stays not-ready until a valid follow-up update arrives. Frames and deltas from retired worlds are diagnosed and ignored; an unannounced world change is still a protocol error.
- `game-state-delta`: state-sync protocol v3 message containing `worldId`, `baseRevision`, `revision`, `serverTimeMs`, and patch operations. `baseRevision` must equal the guest's currently applied authoritative revision. Object fields are set/deleted by path; keyed collections patch records by stable `id`/`playerId`, with indexed additions and optional order data only when existing records reorder.
- `game-state-ack`: guest acknowledges the revision it fully applied. The host validates world and revision and uses ACK progress to detect stale synchronization.
- `game-resync-request`: guest asks for a full state after a missing base revision or failed patch. The host sends only to that peer and retries until acknowledged.
- `game-command`: guest sends a monotonically sequenced command. The host validates its schema and sequence, enforces a 120-command-per-second peer budget, disconnects command floods, and executes accepted commands against its local server.
- `game-client-heartbeat` / `game-host-heartbeat`: bidirectional liveness checks run every two seconds independently of game-state changes, including when the participant is defeated and waiting in the room. A guest missing the 25-second bidirectional round-trip lease is removed from the authoritative world and its transport connection is closed.
- `game-player-defeated` / `game-player-defeated-ack`: Core destruction generates a stable event ID and a targeted defeat notice, retried until acknowledged. Duplicate notices are ACKed but surfaced to the guest only once.

The host computes a structural diff at the 30 Hz replication cadence over the active reliable transport; it does not send complete world frames every tick. Revisions may advance while only transport metadata changes, so empty patches are suppressed and the next non-empty patch covers all mutations since the previous transmitted baseline. On transports that preserve reliable ordering, patches form an exact revision chain. If any state message is lost or the guest finds a base mismatch, it stops applying deltas and requests a full authoritative state instead of guessing.

Do not treat the current transport boundary as a complete hardened security boundary. Additional work before broad public exposure includes authentication/authorization, replay protection across reconnects, rate-limit tuning, and hostile-client tests. The current runtime guard validates known command shapes and rejects unknown command types, but it is not a substitute for full authorization.

## Current implementation boundary

The host-authoritative PeerJS/WebRTC transport includes bounded recovery and participant-lifecycle controls, but still requires real-network browser testing before broad public production exposure. The engine now creates separate human commanders, tracks private resource ledgers, applies per-participant input/selection/aim contexts, and projects the guest view from the authoritative snapshot. A transport disconnect removes the participant record, commander, owned live units, projectiles, and group from the world; structures remain in the world as abandoned structures. Free-for-all and Team create separate cores; Cooperative shares one core. Remaining gaps include session resume (rejoining creates a fresh participant), authentication and room authorization, browser-level end-to-end tests on real networks, TURN configuration, and broader hostile-client testing. The host now bounds commands to 120 per peer per second, rate-limits resync requests, retries full-state delivery a finite number of times, expires guests without bidirectional heartbeats, and explicitly closes stale peer connections. Runtime command shape validation and per-peer sequence deduplication are implemented. Signaling/protocol violations and PeerJS/WebRTC and worker failures are logged and surfaced instead of being swallowed. Multiplayer controller timers isolate per-peer cleanup and message-queue failures so one stale peer cannot stop the host renderer or authoritative simulation. Unhandled failures are surfaced in the room UI and console rather than automatically shutting down the match. Treat direct connectivity as best-effort because TURN is not configured.

## Core destruction and salvage

A non-Core building is operational only while the core identified by its `coreId` is alive; older or AI-owned structures without that field fall back to matching team ID. Core destruction does not delete those buildings: the renderer desaturates them, and the simulation skips their passive repair, weapons, pulses, and production. Inert Harvester and Drone Stations also deactivate their deployed bots/drones. A player may manage only their own structures in Team and Free-for-all; Cooperative mode shares player structures. Foreign and abandoned enemy structures cannot be upgraded, repaired, configured, or dismantled by another player. The world continues after Core destruction so salvage remains possible.

Enemy commander strategy treats Core repair as an emergency: when the Core is damaged and repair is affordable, the AI chooses repair before combat. While a Core is damaged it will not launch an attack objective; if repair is unaffordable it can gather resources or salvage instead. Escort drones clear stale combat approach state when their target leaves the commander's leash and resume the continuous orbit around their commander.

## Strict failure handling

The PeerJS room client validates host IDs, room metadata, channel identity, message envelopes, and payload size. The remote client throws if asked for a session or snapshot before receiving authoritative state; it must never fall back to `new GameEngine()` or a synthetic guest snapshot. Host protocol validation errors are written to the console. Full-state recovery is rate-limited and bounded; a peer that never acknowledges a valid full state is disconnected instead of retrying forever.


## Room management lifecycle

The main menu only creates a room or joins an existing room; it does not ask for a game mode. A newly created room opens the full-screen Room Control Center in `lobby` phase. The host can share the five-letter room code or direct `?room=ABCDE` invitation URL, review the live participant roster, choose Free for All, Team, or Cooperative, remove connected guests, and start the match. The host controller remains the authoritative source of the selected mode; the visible selector is only available while the room is in `lobby` phase and the simulation clock is stopped.

Guests see the same room code/link, roster, current mode, and phase, but cannot change room settings or start/kick participants. In `playing`, an alive participant can close the room manager and return to the game while keeping the room session active. Defeated participants remain connected and can keep the manager/chat open. In `results`, survival times are shown and only the host may return the room to a fresh lobby. `Leave Room` is separate from closing/returning to gameplay: leaving closes the local peer session, whereas returning to gameplay does not disconnect the participant.

The room manager occupies the entire viewport and groups the workflow into invitation details, participant roster, and match settings/actions. The code and complete invite URL are visible in the manager itself, with separate copy controls and immediate success/error feedback. This keeps code/link sharing available even when the HUD is behind the manager and avoids putting mode selection on the main menu.


## Network and room lifecycle boundary

`HostRoomController` owns room phases, participant registration/removal, heartbeat leases, replication baselines, state ACKs, chat validation, and recovery decisions. It depends on the `RoomGameAuthority` interface rather than the concrete `LocalGameServer`; the authority owns simulation state and game rules, while `GameDataTransport` owns message delivery. The PeerJS adapter owns signalling, WebRTC connection state, send-buffer limits, and transport-level close events. A transport error is diagnostic until the underlying WebRTC/ICE state or the liveness/ACK deadlines prove that the path is unhealthy.

Full-state recovery keeps an immutable baseline revision until acknowledged; world changes accumulated during recovery are sent as deltas after the ACK. Transient WebRTC `disconnected` states receive a 12-second recovery window; explicit `failed` states close only the affected peer. The room authority has its own longer, bidirectional heartbeat lease to detect connections that stop delivering application messages even if a browser does not emit a timely close event.
